# Operations

Everything except media blob content, thumbnails, and encryption keys is stored as operations. They form a growing set of immutable CRDT modifications on the library. For example: renaming a photo, creating an album, adding a member. State is determined by the **set** of operations, independent of their order, and is maintained incrementally as each operation arrives.

## Operation and Incremental Merge

Every mutation is an individual immutable CRDT operation. There are no semantic operation groups,
operation UUIDs, parent-operation links, or global replay order.

<SchemaCard title="Operation">
  <Field name="dot" type="Dot { counter: u64, device_id: u128 }" note="Stable operation identity and deterministic tie-break key." />
  <Field name="author" type="LibraryUsername" note="Display/audit metadata only; never used for merge." />
  <Field name="timestamp" type="DateTime<Utc>" note="Display/audit metadata only; never used for merge." />
  <Field name="operation_content" type="OperationContent" />
</SchemaCard>

`device_id` is a random 128-bit identifier generated once per device and persisted. A device
increments its Lamport counter for every local operation and advances it beyond counters observed
from remote operations. The counter is persisted alongside canonical state; on load it must not
be lower than the highest known dot from that device. Dots are ordered by counter, then by the
lexicographic bytes of `device_id`.

The app merges each newly received operation directly into the persisted in-memory CRDT state. Merge
is commutative, associative, and idempotent. Replicas therefore converge despite duplicate or
out-of-order delivery. Persisted state includes winner dots, OR-set tags and removal observations,
tombstones, and replica causal context, not just UI values. Replica causal context supports sync
and duplicate detection. It is not copied onto each operation. Browse views are derived from the
canonical state.

## Operation List

Each operation carries its timestamp (time of write). This is not used in merge logic.

## CRDT Semantics

The materialized library is derived from CRDT state, not from replaying this list in a particular
order. Every entity can have a placeholder state because an operation may arrive before its
creation. A placeholder is never visible; only the corresponding creation operation sets
`created = true`.

| Operation | Merge representation |
| --- | --- |
| `MediaCreation` | Immutable creation record keyed by `media_id`, with a deterministic dot tie-break for the impossible-in-normal-use same-ID conflict. |
| `MediaRename` | LWW register of `Option<MediaName>`. |
| `MediaPropsUpdate` | Per-key LWW string register. |
| `AlbumCreation` | Marks the entity created and writes `name` and desired parent to their LWW registers using the creation dot. |
| `AlbumMediaAdd` / `AlbumMediaRemove` | Add-wins observed-remove set. An add stores its dot; a remove carries the exact `observed: Set<Dot>` of add dots it cancels. |
| `AlbumDeletion` | Permanent tombstone. It hides the album and its contents without erasing their CRDT metadata. |
| `AlbumRename` | LWW name register. |
| `AlbumReparent` | LWW desired-parent register, followed by deterministic acyclic parent projection. |
| `AlbumThumbnailSet` | LWW `Option<MediaUuid>` register. |
| `GroupCreation` | Immutable creation record keyed by `group_id`; its parent is permanently fixed. |
| `GroupMediaAdd` / `GroupMediaRemove` | Add-wins observed-remove set; a remove carries the exact `observed: Set<Dot>` of add dots it cancels. |
| `GroupDeletion` | Permanent tombstone. |

An LWW register compares dots, never wall-clock timestamps. An entity is visible only when it is
created, not tombstoned, and has a live resolved ancestor chain. Membership is add-wins only
within its OR-set: an add concurrent with deletion of its containing album or group is retained
in canonical state but is not visible. This is deliberately **add-wins unless the container is
tombstoned**. There is intentionally no `MediaDeletion`: media may leave albums and groups but
remains in the library. Album and group tombstones are permanent; there is currently no restore
operation. A future restore feature requires explicit CRDT semantics.

For an LWW register of `Option<T>`, `None` is an ordinary value written with a dot. Clearing a
name, thumbnail, or parent must never be represented by omitting an operation.

For album parentage, replicas select each live album's desired parent from its LWW register. A
reference to a missing, uncreated, or tombstoned parent makes the album temporarily invisible.
For each remaining parent cycle, replicas sever the edge with the lowest winning dot and treat
that album as rooted. This produces one deterministic acyclic forest. Groups cannot be
reparented; that is a product and UI constraint, not an implementation accident.

## File Format

Every operation transport file is serialized as CBOR and encrypted before being written to the
remote. Transport may batch operations for efficiency, but batches have no semantic identity and do
not affect merge results. The exact replacement for the existing remote compaction layout is
intentionally out of scope for this CRDT refactor and will be specified separately.

The remaining compaction and local-log sections below describe the **legacy implementation**.
They will be removed when the new operation transport and persisted CRDT state are implemented; they
are not part of the target CRDT format.

### Legacy compaction format

Each legacy op file is named by a UUID with a tier-dependent extension:

- A **compaction file** (`.op{N}_{count}`) holds many op groups. Its name is a fresh random UUID assigned to the file itself, `N` is the tier, and `count` is the total number of operations inside, summed across every op group in the file. The count is readable from the filename without decrypting the file.

## Compaction

Even if the operation group set as a whole is growing, and each group immutable, the way they are stored in remotes can sometimes change.
We do this to bound the total number of operation files, and the number of files we have to touch to add new groups. To do this we use a Log-Structured Merge-trees (LSM) inspired algorithm.

### Local vs Remote

Compaction never happens locally. The two sides store ops differently:

- **Local** keeps a single append file, `local_state/operations.log`, that accumulates op groups as you make changes. It is never compacted. There is also a `pending.op` file that accumulates groups waiting to be pushed, until it is flushed or grows too large.
- **Remote** stores ops as tiered files and compacts them in the background. The advantage of this is that all compacted states are independent for all remotes, so any change to the procedure can be implemented without problems.


### Compaction File Format

Compaction is built on op group identity: every group has a unique `op_id`, and a compaction file is just the full op groups it covers, each tagged by its `op_id`.

<SchemaCard title="Compaction file (.op{N}_{count})" description="A remote-only file packing op groups together, {count} being their total operation count. Immutable and self-contained.">
  <Field name="tier" type="u8" />
  <Field name="contents" type="Vec<{ op_id: OpUuid, group: OperationGroup }>" />
</SchemaCard>


### Compaction Tiers

Files are organized into tiers. Tier 0 holds raw op groups; higher tiers hold compaction files that pack more and more groups together.

Two limits govern the files at each tier: how many operations a single file at that tier may hold (summed across every op group packed into it), and how many files may exist at that tier before compaction is triggered. Because each compaction file encodes its total operation count in its filename, clients can evaluate both limits from the directory listing alone.

| Tier | File extension | Ops limit | Tier files limit |
|------|---------------|--------------|------------------|
| 1 | `.op1_{count}` | 20 | 10 |
| 2 | `.op2_{count}` | 200 | 10 |
| N | `.opN_{count}` | 20×10^(N-1) | 10 |

With this scheme, the maximum number of operations storable with tier i or less:

| Max tier | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|----------|---|---|---|---|---|---|---|
| Max total ops | 200 | 2,200 | 22,200 | 222,200 | 2,222,200 | 22,222,200 | 222,222,200 |
| Max compacted op files | 10 | 20 | 30 | 40 | 50 | 60 | 70 |

### Compaction Procedure

When any tier has more files than its file limit, the client responsible for this must compact it. The goal is to completely evict that tier. All its files are merged into a single file at the next tier up, leaving no underpopulated file behind. For now this is done greedily in arbitrary order.

1. The client acquires a global operations lock file on the remote, preventing concurrent compactions.
2. It reads all files at tier N and merges their op-group lists into a single new compaction file at tier N+1. "All files at tier N" means all tier-N files recorded in the pushing client's own last known state for that remote (see [Sync](./sync)), not a fresh listing of the remote. A client never lists or reads remote op files outside of what it already knows about to decide what to compact.
3. The tier-N source files are deleted, still under the same lock.
4. If tier N+1 now exceeds its file limit, the procedure is applied again at that tier, cascading upward until no tier is over its limit, all while continuing to hold the same lock acquired in step 1.
5. Once no tier is over its limit, the lock is released.

### Uploading Operations

When pushing, the client writes new operation groups directly as a single compaction file, at the lowest tier whose ops limit can hold the whole batch's total operation count. A push totaling 200 operations, for example, lands directly at tier 2 rather than as an oversized tier-1 file, regardless of how many op groups those operations are split across.

## Local Log Format

`operations.log` is an append-only binary file that lists all the operation groups. It is a sequence of frames like this:

```
blob_len   4 bytes   unsigned 32-bit integer
blob      blob_len   CBOR-serialized OperationGroup, encrypted
```

Operation IDs are kept inside the encrypted CBOR payload, so every frame must be decrypted before it can be used. `blob_len` must be greater than zero and no larger than 64 MiB. Any malformed, incomplete, or unauthenticated frame, including the final frame, makes the log unreadable. Repair is intentionally not automatic.

Safety properties:

- A bit flip in the encrypted blob causes authenticated decryption to fail. A changed length either produces an invalid frame or changes the bytes passed to decryption, which also fails.
- The log is written in append mode. A process killed during an append can leave only an incomplete final frame; loading detects that frame and refuses to load rather than silently using a partial log.
- Repair is not automatic.
- The writer does not request that the operating system flush appended bytes to durable storage. These guarantees therefore cover process interruption and malformed on-disk data, not durability across a power loss or operating-system crash.

Rolling out our own format is questionable, but it is the simplest way I found to append operations without rewriting everything each time. We may revisit it when we decide how to persist computed state and computed properties. I am not sure that using SQLite, for example, would be the best solution.
