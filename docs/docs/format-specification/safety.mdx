# Safety

{/*
## What we care about

- **Successful procedures preserve data.** Fetch and push only add or merge data.
- **Procedures are interruption-safe.** They may be killed at any point and safely resumed or repeated.
- **Rust prevents data races.** Its type and ownership systems prevent data races in concurrent code.
- **Corruption is detected.** Data is validated before use.
- **Media files cannot currently be deleted.** Removing media from an album or group does not delete its file.
- **Destructive file access is unrepresentable.** Code that deletes or overwrites a media file must not compile.
*/}

### Sync policy

`SyncPolicy` enforces runtime exclusions. A guard is held until fetch or push
returns; a conflicting acquisition fails with `AlreadyRunning`.

| Procedures started concurrently | Same remote | Different remotes |
| --- | --- | --- |
| Fetch + fetch | <span className="safety-denied">Denied</span> | <span className="safety-denied">Denied</span> |
| Fetch + push | <span className="safety-denied">Denied</span> | <span className="safety-allowed">Allowed</span> |
| Push + push | <span className="safety-denied">Denied</span> | <span className="safety-allowed">Allowed</span> |

### Existing resource restrictions

| Restriction | Protects | Effect |
| --- | --- | --- |
| Local operation-log mutex | `operations.log` | Serializes one synchronous operation-log access at a time. The guard is released before an `await`. |
| Per-remote media-inventory mutex | `remotes/{remote_id}/state/media/media_list.json` | Serializes synchronous inventory read-modify-write work. It is never held across a network await. |
| In-memory operation-state `RwLock` | Reconstructed in-memory state | Multiple readers may coexist; rebuilding installs state under the exclusive write lock. |
| Remote compaction lock file | `operations/LOCK.op` | Only the client that created the lock with `put_if_absent` may compact. A client that cannot create it skips compaction. A stale lock requires manual removal. |

### Access boundaries

To restrict remote-storage access, fetch receives only `StorageRead`, while push
receives `StorageReadWrite`.

Local-state subdirectory access is not strictly enforced. However, path builders
are separated by domain, so each caller receives a focused handle for the part of
local state it needs.

The safety assessments below apply to concurrent work within one `Library`
instance.

#### In-memory state

| Resource | Fetch implementation input | Push implementation input | Local-edit implementation input | Safe? |
| --- | --- | --- | --- | --- |
| Reconstructed in-memory state | Operation-state `RwLock` (through `Library`) | Operation-state `RwLock` (through `Library`) | Operation-state `RwLock` (through `Library`) | <span className="tag tag-ok">Safe</span> `RwLock` |

#### Remote storage

| Resource | Fetch implementation input | Push implementation input | Local-edit implementation input | Safe? |
| --- | --- | --- | --- | --- |
| Remote storage | `StorageRead` | `StorageReadWrite` | Not used | <span className="tag tag-ok">Safe</span> Only one sync operation per remote |

#### Local state

| Resource | Fetch implementation input | Push implementation input | On-demand media download input | Local-edit implementation input | Safe? |
| --- | --- | --- | --- | --- | --- |
| `local_state/library/` | `LocalStateLibraryDir` | Not used | Not used | Not used | <span className="tag tag-ok">Safe</span> Only one fetch per library |
| `remotes/{remote_id}/state/operations/` | `RemoteLastKnownStateDir` | `RemoteLastKnownStateDir` | Not used | Not used | <span className="tag tag-ok">Safe</span> Only one sync operation per remote |
| `remotes/{remote_id}/state/merged_remote_files.json` | `RemoteMergedRemoteFiles` | Not used | Not used | Not used | <span className="tag tag-ok">Safe</span> Fetch-exclusive; corruption intentionally fails fetch |
| `remotes/{remote_id}/state/media/media_list.json` | `RemoteMediaList` | `RemoteMediaList` | `RemoteMediaList` | Not used | <span className="tag tag-ok">Safe</span> Per-remote inventory mutex plus atomic writes |
| `local_state/media/` | Not used | `LocalStateMediaDir` | `LocalStateMediaDir` (through `Library`) | `LocalStateMediaDir` (through `Library`) | <span className="tag tag-ok">Safe</span> Atomic write; immutable file with a 1-to-1 filename/content relation |
| `operations.log` | `LocalOpsReadWriteLock` | `LocalOpsReadWriteLock` (through `Library`) | Not used | `LocalOpsReadWriteLock` (through `Library`) | <span className="tag tag-ok">Safe</span> Mutex |

#### Remote media inventory

The sibling path accessors enforce ownership within the shared `state/` parent: 
`RemoteLastKnownStateDir` owns only the remote's last-known operation state, `RemoteMergedRemoteFiles` owns only the
merge marker, and `RemoteMediaList` owns only the media inventory.

`media_list.json` is a positive-only inventory: an entry means the client has confirmed a media
blob on that remote through one of its three writers: fetch after a successful remote existence
check, push after a successful ensure-present upload, or an on-demand media download after the
blob has been validated. Its absence means unconfirmed, not absent from the remote.

Fetch checks are optional bookkeeping, so an inventory write failure cannot prevent a validated
operation fetch. The three writers use a per-remote non-async mutex, held only for synchronous
local load-modify-save work and never across `exists`, `get`, or `put_if_absent` awaits. Atomic
file replacement prevents partial JSON contents; the mutex prevents lost concurrent updates.

`merged_remote_files.json` is written only by fetch. The global fetch slot makes it fetch-exclusive
within a `Library` instance, and corruption of this merge marker intentionally fails fetch.
