# Versioning

Lasco has no single format version. Only the layers that cross a device boundary, or that cannot
be rebuilt from something else, carry a version indicator. Everything that is device local and
regenerable is left unversioned and evolves through its serde representation instead.

Each version that does exist is checked by strict equality against the constant compiled into the
current build. There is no range of accepted versions and no migration path: a value that does not
match the expected one is rejected with an error.

| Layer | Constant | Current value | Defined in |
|---|---|---|---|
| Encrypted blob | `BLOB_FORMAT_VERSION` | `1` (`u8`) | `encryption/blob.rs` |
| Master key file | `PROTOCOL_VERSION` | `1` (`u32`) | `library/mod.rs` |
| Library directory | `LIBRARY_FORMAT_VERSION` | `1` (`u32`) | `library/mod.rs` |
| Local operation log | `LOCAL_OP_LOG_FORMAT_VERSION` | `1` (`u32`) | `operations/local_ops.rs` |
| S3 secret key | `S3_SECRET_ENCRYPTION_DESCRIPTION` | `"AES-256-GCM v1"` | `s3_secret.rs` |

`config.json`, `library.json`, and the CRDT snapshot carry no version field. See
[Unversioned formats](#unversioned-formats).

---

## Encrypted blob format

Every encrypted blob begins with a single byte version header, followed by the XChaCha20 nonce
and the ciphertext:

```
[ format_version: u8 (1 byte) | nonce: 24 bytes | ciphertext ]
```

This envelope is shared by media files (`.data`), thumbnails (`.thumb`), remote operation files
(`.op`), the CRDT snapshot, and each frame of the local operation log. Decoding a blob whose first
byte is not `BLOB_FORMAT_VERSION` fails with an unknown blob format version error.

The version covers the envelope only. It says nothing about the shape of the plaintext inside,
which is versioned separately where it is versioned at all.

---

## Master key protocol version

Each per-user master key file (`mk_{username}_{uuid}.enc`) stores a big endian `u32` before the
AES-GCM nonce and the ciphertext:

```
[ protocol_version: u32 (4 bytes, big endian) | nonce: 12 bytes | ciphertext ]
```

The constant is named `PROTOCOL_VERSION` and lives in `library/mod.rs`, but the master key file is
the only place it is written or checked.

---

## Library directory format

The library format version is an empty sentinel file whose name encodes the version. The filename
is derived from `LIBRARY_FORMAT_VERSION` by `library_format_sentinel()`, so the number and the name
cannot drift apart:

```
local_state/library/
  version_1
```

It is written on init, next to `library_id_{uuid}`, `library_salt`, and the master key files.
`Library::open` requires the file named `version_1` to be present in the local library directory
and fails otherwise, so a directory written by a build with a different sentinel name is refused.

This is the one coarse gate for the on-disk layout. It is meant to be incremented only for a
change an older build must not open at all, not for the ordinary addition of a field to a config
file. Note that `config.json` is read before any library is opened, so it sits outside this gate.

`initialize_remote` copies the whole local `library/` directory to a remote, so the sentinel also
ends up under `library/version_1` on the remote. Nothing reads it back from there: the check is
performed against the local copy only.

---

## Local operation log format

`operations.log` begins with a magic value and a little endian `u32` version:

```
[ magic: "LOPS" (4 bytes) | format_version: u32 (4 bytes, little endian) | frames... ]
```

A file that does not start with `LOPS` is treated as the headerless legacy format and read from
byte zero. A file that does start with `LOPS` but carries a version other than
`LOCAL_OP_LOG_FORMAT_VERSION` is rejected.

Each frame after the header is a length prefixed encrypted blob holding one CRDT operation, and
so carries the blob envelope version of its own.

---

## Remote secret key version

There is no separate per remote credential file. S3 credentials live in `library.json`, and the
secret key's version is a plain string tag compared by equality:

```json
{
  "secret_key_encrypted": "...",
  "secret_key_encryption_description": "AES-256-GCM v1"
}
```

Decryption is refused when the description does not match `S3_SECRET_ENCRYPTION_DESCRIPTION`.

---

## Unversioned formats

### Configuration files

`config.json` and `library.json` carry no version field. They are device local and are never
uploaded to a remote, so no other device or build has to agree on their shape.

They evolve through serde instead. A new field is declared with `#[serde(default)]` and backfilled
on first load, then written on the next save. `media_source_order` in `library.json` is the current
example: a file that lacks it is given the ordering implied by the existing per remote priority
fields. Renames use `#[serde(alias)]`. A change that serde cannot express this way is a change to
the library layout, which is what `LIBRARY_FORMAT_VERSION` is for.

The consequence is that an older build reading a file written by a newer one silently drops the
fields it does not know and writes the file back without them. Downgrading an installation, or
copying a library directory onto a device running an older build, is not supported.

### CRDT snapshot

`crdt-state.enc` holds a plain CBOR encoding of `CrdtState` with no wrapper and no version field.
A snapshot that cannot be decoded produces `PersistenceError::Deserialize`, which
`is_recoverable_snapshot_failure` reports as recoverable and the FFI surfaces as
`LascoError::CrdtRecoveryAvailable`. The snapshot is a local cache of state that the operation log
and the remote already hold, so the recovery path is to discard it and rebuild rather than to
migrate it.

### Remote state caches

These are local caches of remote state, refetched when they are missing:

- `remotes/{remote_id}/state/media/media_list.json`
- `remotes/{remote_id}/state/compact_op_id_merged_to_local.json`
- the compaction lock `operations/LOCK.op`

The remote operation files encode their compaction tier and operation count in the filename
(`{uuid}.op{tier}_{count}`) rather than in a version field, and the CBOR payload inside them is
covered only by the blob envelope version.

## Application versions

The version shown in each app's settings screen is the product version and is unrelated to any of
the format versions above.

| Component | Field | Value |
|---|---|---|
| `lasco-core`, `lasco-ffi` | `version` in `Cargo.toml` | `0.1.0` |
| Swift app | `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` | `0.1.0` / `3` |
| Android app | `versionName` / `versionCode` | `0.1.0` / `1` |
